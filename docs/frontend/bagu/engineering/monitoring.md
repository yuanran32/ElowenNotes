# 前端监控

## 一句话结论

前端监控是把用户侧的错误、性能和行为数据采集回来，帮助团队发现线上问题、定位影响范围并验证修复效果。它不是只收 `console.error`，而是一套采集、上报、聚合、告警和分析链路。

## 监控类型

| 类型 | 采集内容 | 价值 |
| --- | --- | --- |
| 错误监控 | JS 错误、资源加载失败、Promise 未处理异常 | 定位线上崩溃和白屏 |
| 性能监控 | FCP、LCP、CLS、INP、接口耗时 | 发现慢页面和性能退化 |
| 行为监控 | 页面访问、点击路径、路由跳转 | 还原问题现场 |
| 接口监控 | 请求状态码、耗时、错误码 | 判断前后端责任边界 |

## 错误采集

```js
window.addEventListener('error', event => {
  // JS 运行错误和资源加载错误
})

window.addEventListener('unhandledrejection', event => {
  // 未处理的 Promise 错误
})
```

框架项目还要接入框架错误处理，例如 Vue 的 `app.config.errorHandler`，否则组件渲染和生命周期中的错误可能缺少上下文。

## 上报策略

1. 使用 `sendBeacon` 或异步请求，降低对页面卸载的影响。
2. 做采样，避免高流量页面产生过多数据。
3. 做去重和聚合，例如按错误信息、堆栈、版本号聚合。
4. 带上环境、版本、路由、用户匿名标识、设备信息。
5. 注意隐私，不上传密码、token、手机号等敏感信息。

## 白屏监控

白屏可以从多个角度判断：

- 根节点是否有有效子节点。
- 首屏关键元素是否出现。
- 页面错误是否集中发生在初始化阶段。
- LCP 或自定义首屏指标是否超时。

工程里最好结合业务关键节点埋点，而不是只靠“body 是否为空”。

## 常见追问

### source map 怎么用于监控？

线上 JS 通常被压缩混淆，错误堆栈难读。发布时把 source map 上传到监控平台，并用版本号关联，平台就能把压缩后的堆栈还原到源码行列。source map 不建议公开给所有用户访问。

### 怎么避免监控影响性能？

采集逻辑要轻量，批量上报，空闲时处理，控制采样率。错误上报不能阻塞主流程，行为录制也要限制频率和数据量。

### 线上报错很多怎么排优先级？

看影响用户数、发生频率、是否阻塞主流程、是否集中在新版本、是否影响核心路径。高频但不影响业务的错误不一定比低频白屏更优先。
